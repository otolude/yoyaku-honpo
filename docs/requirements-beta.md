# Phase 1 β版 要件定義

## 1. 目的

Phase 1では、Discordへの投稿を指定した日時に自動で送信できる予約投稿Botを開発する。

最初は開発者自身が管理する1つのDiscordサーバーで利用し、次のことを安全に行える状態を目指す。

- 日本時間を指定した単発の予約投稿
- 毎日または毎週の定期投稿
- 予約の確認、編集、削除
- 定期投稿の一時停止と再開
- 本文が未入力の下書き予約と事前通知
- 投稿失敗時の再試行と運営者への通知
- Botが停止・再起動しても予約を失わない運用

AI文章生成、文体反映、PAY.JPによる課金はPhase 2以降で扱い、Phase 1には含めない。

## 2. 対象利用者

Phase 1の対象は、環境変数で指定した1つのDiscordサーバーに所属する次の利用者である。

- Discordサーバー管理者
- 環境変数で指定した許可ロールを持つメンバー
- Bot運営者

ここでいう「Bot運営者」は、環境変数にDiscordユーザーIDが登録されている、Botの保守を担当する人物を指す。

一般メンバーはPhase 1では予約を作成できない。対象外のDiscordサーバーでは、すべての操作を拒否する。

## 3. 対象機能

Phase 1では次の機能を実装する。

- Discordのスラッシュコマンドによる操作
- 単発予約投稿
- 毎日同じ時刻に投稿する定期投稿
- 毎週同じ曜日・時刻に投稿する定期投稿
- 予約の一覧表示と詳細表示
- 予約の編集と削除
- 定期投稿の一時停止と再開
- 本文なしの下書き予約
- 下書き予約の事前通知
- 投稿失敗時の再試行
- 投稿失敗や遅延などの運営者通知
- Bot停止後の予約復旧
- 予約と実行結果のPostgreSQLへの保存

投稿できる内容は通常のテキストだけとする。Discordの文字数制限を超える本文は登録できない。

## 4. 対象外機能

次の機能はPhase 1には含めない。

- AIによる文章生成
- 利用者の文体の保存や反映
- PAY.JP連携
- 料金プラン、契約状態、利用回数による制限
- 複数のDiscordサーバーへの対応
- 日本語以外への対応
- Discord以外のサービスへの投稿
- 月次、年次などの繰り返し投稿
- 1つの予約に複数の曜日を指定する週次投稿
- 添付ファイル、画像、動画、埋め込み形式の投稿
- 投稿済みDiscordメッセージの自動編集や削除
- Web管理画面
- 高度な利用統計や分析

## 5. 権限

### 5.1 予約を作成できる利用者

予約を作成できるのは次のいずれかに該当する利用者だけとする。

- Discordサーバー管理者
- 環境変数で指定した許可ロールを持つメンバー

一般メンバーは予約を作成できない。

### 5.2 予約を操作できる利用者

- 予約の作成者は、自分が作成した予約を表示、編集、削除、一時停止、再開できる。
- Discordサーバー管理者は、サーバー内のすべての予約を表示、編集、削除、一時停止、再開できる。
- 管理者ではない利用者は、他人の予約を操作できない。
- Bot運営者であっても、Discord上の予約操作では原則として上記の権限規則に従う。運営者であることだけを理由に予約の操作権限は追加しない。

一時停止と再開は、毎日または毎週の定期投稿だけに使用できる。単発予約は一時停止・再開できず、実行を止める場合は削除する。

権限はコマンドを表示するときだけでなく、各操作を実行する直前にも確認する。

## 6. スラッシュコマンド

Phase 1では、次のスラッシュコマンドを提供する。コマンド名や選択肢はDiscord上で分かりやすい日本語の説明を表示する。

| コマンド | 用途 |
| --- | --- |
| `/post create` | 単発、毎日、または毎週の予約を作成する |
| `/post list` | 操作できる予約の一覧を表示する |
| `/post show` | 予約の詳細を表示する |
| `/post edit` | 予約内容を編集する |
| `/post delete` | 予約を削除する |
| `/post pause` | 定期投稿を一時停止する |
| `/post resume` | 一時停止中の定期投稿を再開する |

操作結果は原則として、コマンドを実行した本人だけに見えるDiscordの返信で表示する。

各予約には、利用者がコマンドで指定しやすい予約IDを付ける。削除時には対象の内容を示し、確認操作を行ってから削除を確定する。

## 7. 予約と定期投稿の仕様

### 7.1 共通仕様

- 対応言語は日本語だけとする。
- 利用者が入力・確認する日時は、すべて `Asia/Tokyo`（日本時間）とする。
- 日時の入力形式は `YYYY-MM-DD HH:MM`（例: `2026-08-20 19:00`）とする。
- 予約は分単位とし、秒は指定しない。
- 新しい予約の日時は、作成時点から5分以上先でなければならない。
- データベースには日時をUTCで保存し、Discord上では日本時間に変換して表示する。
- 投稿先は、対象サーバー内でBotが閲覧と送信を行えるテキストチャンネルから指定する。
- 同じチャンネル、同じ日時、同じ本文の予約がある場合は、作成前に重複の可能性を警告する。
- 投稿処理中の予約は編集または削除できない。
- 次回投稿時刻の5分前を過ぎた予約は編集できない。
- 編集後には、変更後の内容と次回投稿日時を表示する。
- 誰がいつ作成、編集、削除、一時停止、再開したかを記録する。

### 7.2 単発予約

- 指定した日時に1回だけ投稿する。
- 投稿に成功した予約は「完了」状態にする。
- 完了した予約と関連履歴は30日間保存し、30日経過後に自動削除する。
- 完了済みの予約は編集できない。
- 単発予約は一時停止・再開できない。実行を止める場合は予約を削除する。
- 予約を削除しても、すでにDiscordへ投稿されたメッセージは削除しない。

### 7.3 毎日の定期投稿

- 毎日、指定した日本時間の同じ時刻に投稿する。
- 任意の終了日を設定できる。
- 終了日を設定しない場合は、一時停止または削除されるまで継続する。

### 7.4 毎週の定期投稿

- 毎週、指定した1つの曜日と日本時間の同じ時刻に投稿する。
- Phase 1では、1つの予約に複数の曜日を指定できない。
- 任意の終了日を設定できる。
- 終了日を設定しない場合は、一時停止または削除されるまで継続する。

### 7.5 定期投稿の編集、一時停止、再開

- 定期投稿の編集は、次回以降のすべての投稿に適用する。
- 過去に投稿済みのDiscordメッセージや実行履歴は変更しない。
- 一時停止と再開は、毎日または毎週の定期投稿だけに使用できる。
- 一時停止中は投稿を行わない。
- 再開時は、再開した時点より後にある最初の予定日時を次回投稿日時にする。
- 一時停止中に過ぎた回は、再開時にまとめて投稿しない。
- 定期投稿を削除すると、今後のすべての投稿を停止する。
- 終了日の判定には `Asia/Tokyo` の日付を使用し、終了日当日の予定投稿は実行対象に含める。
- 終了日当日の最後の予定投稿を処理した後、定期投稿を `ended` 状態にする。
- `ended` 状態の予約は今後投稿せず、編集、一時停止、再開もできない。

### 7.6 予約の状態

予約状態は、予約全体が今後どのように動くかを表す。予約は少なくとも次の状態を持つ。

- `draft`（下書き）: 本文が未入力
- `active`（有効）: 投稿可能
- `paused`（一時停止）: 利用者が定期投稿を停止中
- `failed`（失敗）: 単発投稿が最終的に失敗し、運営者の確認が必要
- `completed`（完了）: 単発投稿が成功済み
- `ended`（終了済み）: 終了日を迎えた定期投稿
- `deleted`（削除済み）: 利用者が削除済み

本文と予約状態の関係は次のとおりとする。

- `draft` は本文が未入力であり、`content` はNULLとする。
- `paused` は、削除前の編集状態に応じて本文なし・本文ありのどちらも許可する。
- `deleted` は削除前の本文をそのまま保持する。本文なしの `draft` または `paused` を削除した場合は、NULLのままとし、ダミー本文を保存しない。
- `active`、`failed`、`completed`、`ended` は本文を必須とする。

各回の投稿結果は、予約状態とは分けて実行履歴へ保存する。実行履歴は少なくとも次の状態を持つ。

- `pending`（実行待ち）: 予定されているが、まだ処理を始めていない
- `processing`（処理中）: 最初の送信または再試行を実行中
- `succeeded`（成功）: Discordへの投稿に成功した
- `failed`（失敗）: その回の投稿が最終的に失敗した
- `skipped`（見送り）: 下書き、Bot停止中の期限超過などにより投稿しなかった

定期投稿の1回が失敗しても、予約自体は原則として `active` を維持し、次回予定を実行する。単発投稿の最終失敗時だけ、予約自体を `failed` にする。

予約一覧は、初期状態では今後の予約を日時が近い順に1ページ10件表示する。予約ID、投稿先、次回投稿日時、繰り返し方法、状態、本文の先頭部分を表示し、状態による絞り込みを可能にする。状態を指定しない通常一覧から削除済み予約を除外し、`deleted` を明示した場合だけ表示する。非管理者は削除済みを含めて自分の予約だけを、管理者は対象サーバー内の全作成者の予約を表示できる。削除済み予約の詳細と本文も、作成者本人または管理者だけが表示できる。存在しない予約と閲覧権限のない予約には同じ応答を返し、30日後の物理削除後は取得できない。

## 8. 下書きと通知

- 本文なしでも予約を作成でき、その予約を「下書き」とする。
- 下書きには、投稿予定日時、投稿先、繰り返し方法など、本文以外の予約情報を保存する。
- 本文が入力された時点で、有効な予約へ変更する。
- 投稿予定時刻の24時間前に、本文が未入力なら作成者へDMで通知する。
- 投稿予定時刻の1時間前にも、本文が未入力なら作成者へDMで再通知する。
- 作成時点ですでに24時間前を過ぎている場合、24時間前の通知は送らず、まだ過ぎていない次の通知だけを送る。
- 作成時点ですでに1時間前を過ぎている場合、作成直後に本文未入力であることを作成者へ通知する。
- 作成者へDMを送れない場合は、環境変数で指定した運営者通知チャンネルへ通知する。
- 下書きのまま予定時刻を迎えた場合は投稿せず、その回を `skipped` として運営者通知チャンネルへ通知する。
- 単発の下書き予約は `draft` のまま残し、自動投稿しない。作成者または管理者が本文と新しい未来の日時を設定するか、予約を削除する。
- 定期投稿では本文がない回の実行履歴を `skipped` として記録し、予約自体は下書きのまま次回予定を維持する。
- 一時停止中の定期投稿には事前通知を送らない。

通知には、予約ID、投稿予定日時、投稿先、必要な対応を含める。ただし、Botトークンなどの秘密情報は含めない。

運営者通知チャンネルへ投稿できない場合は、環境変数で指定したBot運営者へDMを試す。チャンネル通知とDMの両方に失敗した場合は、エラーをログへ残す。通知には秘密情報や内部の例外全文を含めない。

## 9. 失敗時の再試行

最初の送信を1回行い、一時的な通信障害などで失敗した場合は、次の間隔で最大3回再試行する。

1. 1分後
2. 5分後
3. 15分後

したがって、最大試行回数は最初の送信1回と再試行3回を合わせた合計4回である。

Discordから再試行までの待機時間を指定された場合は、その指示を優先する。

次のように再試行しても解決しないと判断できる場合は、再試行せず直ちに失敗とする。

- Botに投稿権限がない
- 投稿先チャンネルが削除されている、または存在しない
- Botが対象サーバーから退出している
- 投稿内容がDiscordの制限に違反している

最大回数の再試行に失敗した場合は、その実行を失敗として記録し、運営者通知チャンネルへ通知する。

単発予約は `failed` 状態にする。定期投稿では失敗した回の実行履歴を `failed` とし、予約自体は原則として `active` を維持して次回予定を実行する。

各実行には一意な識別情報を持たせ、同じ実行を重複して送信しないようにする。送信結果が不明な場合も、無条件に再送して二重投稿を発生させない設計とする。

## 10. Bot停止・復旧時の動作

- 予約と実行状態はPostgreSQLへ保存し、Botを再起動しても失われないようにする。
- Bot起動時に、未完了の予約と投稿処理をデータベースから読み込み直す。
- 同じBotが複数起動した場合でも、同じ予約を二重実行しないようデータベースを使って排他制御する。

### 10.1 期限を過ぎた単発予約

Bot復旧時に単発予約の予定時刻を過ぎていた場合は、次のように処理する。

- 予定時刻から15分以内なら、遅延投稿を行う。
- 15分を超えていたら自動投稿せず、予約を `failed` 状態にする。
- 遅延投稿を行う場合も、自動投稿しない場合も、運営者通知チャンネルへ通知する。

15分以内の遅延投稿がDiscordへの送信エラーになった場合は、通常の再試行ルールを適用する。

### 10.2 期限を過ぎた定期投稿

- Bot停止中に過ぎた回は投稿しない。
- 抜けた回数と停止していた期間を実行履歴へ記録する。
- 復旧時点より後にある最初の予定日時を計算し、次回投稿とする。
- 投稿できなかった回があることを運営者通知チャンネルへ通知する。

### 10.3 投稿処理中に停止した場合

- 起動時に未完了の投稿処理を検出する。
- Discordへの送信が成功したか確認できない場合は、二重投稿防止を優先する。
- 自動で安全に再開できない実行は、実行履歴を `failed` として運営者へ確認を依頼する。単発予約は `failed`、定期投稿の予約は原則として現在の予約状態を維持する。

## 11. データ保存

### 11.1 データベース

- データベースにはPostgreSQLを使用する。
- 開発環境のPostgreSQLはDocker Composeで起動する。
- PythonアプリケーションはDockerコンテナ内ではなく、WSL上の `.venv` で実行する。
- PostgreSQLの接続先や認証情報は環境変数で設定する。
- 開発、テスト、本番のデータベースと認証情報を分離する。

### 11.2 保存する主なデータ

- 予約ID
- 対象DiscordサーバーID
- 作成者のDiscordユーザーID
- 投稿先チャンネルID
- 投稿本文
- 単発、毎日、毎週の種別
- 毎週投稿の曜日
- 次回投稿日時
- 任意の終了日
- 予約状態
- 再試行回数と次回再試行日時
- 作成日時と更新日時
- 作成、編集、削除、一時停止、再開を行った利用者と日時、およびシステムによる単発完了、失敗、定期終了の履歴
- 各回の予定日時、実行日時、結果、エラーの概要
- Discordへ投稿できた場合のメッセージID
- 下書き通知の送信日時と結果

Discordの表示名やチャンネル名は変更される可能性があるため、識別にはDiscordが発行するIDを使用する。

`completed`、`ended`、`deleted` 状態の予約と、それらに関連する履歴は30日間保存し、30日経過後に自動削除する。`failed` 状態の予約は運営者が確認するまで自動削除しない。自動削除を実行する具体的な定期処理方式は技術設計で決める。運用に必要なバックアップと復元手順を用意する。

## 12. セキュリティ

- Discord Botトークン、データベースのパスワードなどの秘密情報をGitへコミットしない。
- ローカル環境では `.env` を使用し、Gitには秘密情報を含まない `.env.example` だけを置く。
- 対象DiscordサーバーID、許可ロールID、Bot運営者ユーザーID、運営者通知チャンネルIDを環境変数で指定する。
- Botには動作に必要な最小限のDiscord権限だけを与える。
- コマンド実行時に、対象サーバー、利用者のロール、管理者権限、予約の所有者を確認する。
- Phase 1では、すべての利用者について `@everyone` と `@here` の使用を禁止する。
- 予約の登録・編集時に `@everyone` と `@here` を拒否する。
- Discordへ送信するときは `allowed_mentions` を明示的に指定し、`@everyone` と `@here` が通知として働かないよう制限する。
- ユーザーやロールへの通常メンションも、意図しない通知を防ぐため、Phase 1では原則として解析・通知しない設定にする。
- ログや運営者通知にBotトークン、データベース認証情報、接続文字列を出力しない。
- 運営者通知チャンネルへ投稿できない場合はBot運営者へのDMを試し、両方に失敗した場合はログへ記録する。
- 運営者への通知には秘密情報や内部の例外全文を含めない。
- 利用者向けのエラー表示には内部の例外全文を載せず、必要な対応を日本語で示す。
- データベースのバックアップはアクセスを制限し、復元できることを確認する。

## 13. β版の完成条件

次の条件をすべて満たしたとき、Phase 1のβ版を完成とする。

### 13.1 基本機能

- [ ] 環境変数で指定した1つのDiscordサーバーだけで利用できる。
- [ ] 操作とメッセージが日本語で提供される。
- [ ] 日時がすべて日本時間で入力・表示される。
- [ ] 権限のある利用者がスラッシュコマンドで単発、毎日、毎週の予約を作成できる。
- [ ] 単発予約が予定日時に1回だけ投稿される。
- [ ] 毎日および毎週の定期投稿が予定どおり実行される。
- [ ] 予約の一覧と詳細を確認できる。
- [ ] 権限のある利用者が予約を編集・削除できる。
- [ ] 定期投稿を一時停止・再開でき、停止中の回がまとめて投稿されない。
- [ ] 単発予約は一時停止・再開できず、削除によって停止できる。
- [ ] 終了日当日の投稿後に定期投稿が `ended` になり、それ以後実行・編集・一時停止・再開されない。

### 13.2 権限

- [ ] サーバー管理者と許可ロールを持つメンバーだけが予約を作成できる。
- [ ] 一般メンバーは予約を作成できない。
- [ ] 作成者は自分の予約を操作できる。
- [ ] サーバー管理者はサーバー内のすべての予約を操作できる。
- [ ] 管理者ではない利用者は他人の予約を操作できない。

### 13.3 下書きと通知

- [ ] 本文なしの予約を下書きとして保存できる。
- [ ] 下書きの24時間前と1時間前に作成者へDM通知できる。
- [ ] DMできない場合に運営者通知チャンネルへ通知できる。
- [ ] 下書きのまま予定時刻になった投稿は送信されない。
- [ ] 下書きで投稿されなかった回が、決められた状態と履歴で記録される。

### 13.4 障害と復旧

- [ ] 最初の送信に失敗した場合、1分後、5分後、15分後に最大3回再試行し、初回を含めて最大4回試行する。
- [ ] 権限不足など回復不能なエラーは再試行せず失敗にできる。
- [ ] 最終的な失敗が運営者通知チャンネルへ通知される。
- [ ] 運営者通知チャンネルへ投稿できない場合はBot運営者へDMし、両方に失敗した場合はログへ記録される。
- [ ] 同じ予約が二重投稿されない。
- [ ] Botを再起動しても予約が失われない。
- [ ] 期限から15分以内の単発予約が復旧後に遅延投稿され、運営者へ通知される。
- [ ] 期限から15分を超えた単発予約が投稿されず `failed` 状態になり、運営者へ通知される。
- [ ] Bot停止中に過ぎた定期投稿が投稿されず、次の予定から再開される。

### 13.5 データとセキュリティ

- [ ] 開発環境のPostgreSQLをDocker Composeで起動できる。
- [ ] PythonアプリケーションをWSL上の `.venv` から実行できる。
- [ ] 予約、実行履歴、通知結果がPostgreSQLへ保存される。
- [ ] 予約状態と各回の実行結果が分けて保存される。
- [ ] `completed`、`ended`、`deleted` と関連履歴が30日後に自動削除され、未確認の `failed` は自動削除されない。
- [ ] 開発、テスト、本番のデータベース設定が分離される。
- [ ] 秘密情報がGitやログへ保存されない。
- [ ] `@everyone` と `@here` を含む本文の登録・編集が拒否される。
- [ ] Discord送信時の `allowed_mentions` が明示的に制限される。

### 13.6 品質と運用

- [ ] 予約日時の計算、権限判定、状態変更、再試行、停止後の復旧に自動テストがある。
- [ ] DiscordやPostgreSQLの障害を想定した自動テストがある。
- [ ] 単発、毎日、毎週について、予約作成から投稿までを対象サーバーで手動確認できる。
- [ ] Bot停止、再起動、遅延、投稿失敗の手動確認が完了している。
- [ ] セットアップ、起動、停止、バックアップ、復元、障害確認の手順が文書化されている。
- [ ] 別の開発環境でも、手順に従ってPostgreSQLとBotを起動できる。
