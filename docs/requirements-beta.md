# Phase 1 β版 要件定義

## 1. 目的

Phase 1では、Discordへの投稿を指定した日時に自動で送信できる予約投稿Botを開発する。

最初は開発者自身が管理する1つのDiscordサーバーで利用し、次のことを安全に行える状態を目指す。

- 日本時間を指定した単発の予約投稿
- 毎日または毎週の定期投稿
- 予約の確認、編集、削除
- 定期投稿の一時停止と再開
- 本文が未入力の下書き予約と事前通知
- 投稿失敗時の再試行と運営者への通知
- Botが停止・再起動しても予約を失わない運用

AI文章生成と決済・契約管理はPhase 1には含めず、現在の[開発・公開ロードマップ](development-roadmap.md)に従って後続段階で扱う。正式リリースではサブスクリプション契約を導入するが、利用者の文体学習、過去投稿学習、Embedding、利用者プロフィール生成は採用しない。

## 2. 対象利用者

Phase 1の対象は、環境変数で指定した1つのDiscordサーバーに所属する次の利用者である。

- Discordサーバー管理者
- 環境変数で指定した許可ロールを持つメンバー
- Bot運営者

ここでいう「Bot運営者」は、環境変数にDiscordユーザーIDが登録されている、Botの保守を担当する人物を指す。

一般メンバーはPhase 1では予約を作成できない。対象外のDiscordサーバーでは、すべての操作を拒否する。

## 3. 対象機能

Phase 1では次の機能を実装する。

- Discordのスラッシュコマンドによる操作
- 単発予約投稿
- 毎日同じ時刻に投稿する定期投稿
- 毎週同じ曜日・時刻に投稿する定期投稿
- 予約の一覧表示と詳細表示
- 予約の編集と削除
- 定期投稿の一時停止と再開
- 本文なしの下書き予約
- 下書き予約の事前通知
- 投稿失敗時の再試行
- 投稿失敗や遅延などの運営者通知
- Bot停止後の予約復旧
- 予約と実行結果のPostgreSQLへの保存

投稿できる内容は通常のテキストだけとする。Discordの文字数制限を超える本文は登録できない。

## 4. 対象外機能

次の機能はPhase 1には含めない。

- AIによる文章生成
- 利用者の文体の保存や反映
- PAY.JP連携
- 料金プラン、契約状態、利用回数による制限
- 複数のDiscordサーバーへの対応
- 日本語以外への対応
- Discord以外のサービスへの投稿
- 月次、年次などの繰り返し投稿
- 1つの予約に複数の曜日を指定する週次投稿
- 添付ファイル、画像、動画、埋め込み形式の投稿
- 投稿済みDiscordメッセージの自動編集や削除
- Web管理画面
- 高度な利用統計や分析

## 5. 権限

### 5.1 予約を作成できる利用者

予約を作成できるのは次のいずれかに該当する利用者だけとする。

- Discordサーバー管理者
- 環境変数で指定した許可ロールを持つメンバー

一般メンバーは予約を作成できない。

### 5.2 予約を操作できる利用者

- 予約の作成者は、自分が作成した予約を表示、編集、削除、一時停止、再開できる。
- Discordサーバー管理者は、サーバー内のすべての予約を表示、編集、削除、一時停止、再開できる。
- 管理者ではない利用者は、他人の予約を操作できない。
- Bot運営者であっても、Discord上の予約操作では原則として上記の権限規則に従う。運営者であることだけを理由に予約の操作権限は追加しない。

一時停止と再開は、毎日または毎週の定期投稿だけに使用できる。単発予約は一時停止・再開できず、実行を止める場合は削除する。

権限はコマンドを表示するときだけでなく、各操作を実行する直前にも確認する。

## 6. スラッシュコマンド

Phase 1では、次のスラッシュコマンドを提供する。コマンド名や選択肢はDiscord上で分かりやすい日本語の説明を表示する。

| コマンド | 用途 |
| --- | --- |
| `/post create` | 単発予約を作成する |
| `/post create-daily` | 毎日予約を作成する |
| `/post create-weekly` | 毎週予約を作成する |
| `/post list` | 操作できる予約の一覧を表示する |
| `/post show` | 予約の詳細を表示する |
| `/post edit` | 予約IDを選び、変更項目を直接指定して編集する |
| `/post delete` | 予約を削除する |
| `/post pause` | 定期投稿を一時停止する |
| `/post resume` | 一時停止中の定期投稿を再開する |

操作結果は原則として、コマンドを実行した本人だけに見えるDiscordの返信で表示する。

編集は `/post edit public_id:<canonical UUIDv7> channel:<任意> scheduled_at:<単発用、任意>
local_time:<定期用、任意> weekday:<毎週用、任意> end_date:<定期用、任意>
content:<任意> clear_content:<任意、既定false> clear_end_date:<任意、既定false>` とする。
予約IDをAutocomplete候補から選び、変更項目を直接指定する短縮・上級者向け経路とする。詳細画面の「✏️ 編集」は画面を確認しながら編集する一般利用者向け経路であり、両方を提供する。確認画面、View、Modalは使用せず、明示された変更を即時反映する。`local_time`は毎日・毎週予約の基本投稿時刻を恒久的に変更し、今回だけ投稿時刻を変更する用途には使用しない。一時停止中も既存仕様で許可された項目を直接編集できる。変更項目を1つ以上指定しなければならない。未指定と値の削除を
区別するため本文と終了日にはclearオプションを設け、値との同時指定、変更指定なし、
実際の変更がない操作を拒否する。変更指定なしと、明示値が現在値と同じno-opは区別する。予約種別、対象サーバー、作成者、予約IDは変更できず、
種別変更は現在の予約を削除して希望種別で新規作成する。

単発は投稿先、投稿日時、本文、毎日は投稿先、投稿時刻、終了日、本文、毎週は投稿先、
曜日、投稿時刻、終了日、本文を編集できる。本文は作成時と同じ制限を適用する。投稿先は
設定サーバー内でBotが閲覧・送信できるテキストチャンネルだけとする。

各予約には、利用者がコマンドで指定しやすい予約IDを付ける。削除時には対象の内容を示し、確認操作を行ってから削除を確定する。

削除は `/post delete public_id:<UUIDv7> reason:<任意、最大500文字>` とする。コマンド実行時は最新の対象と権限を読み取り専用で確認し、本人だけが操作できる非永続の確認Viewを120秒間表示する。削除ボタン時に最新状態を再検証して削除し、確認中はDB Sessionやトランザクションを保持しない。理由未指定時は`理由未入力`を保存するが、管理者が同じguildの他作成者予約を削除する場合だけ、前後空白を除去した1～500文字の理由を必須とし、空白だけを拒否して固定理由へ変換しない。理由はOperationLogの監査用に保存し、利用者向け応答や通常ログへ全文を複製しない。不存在、権限不足、状態不許可、処理中には同じ応答を返す。

単発予約の作成は `/post create channel:<テキストチャンネル> scheduled_at:<日時> content:<任意> allow_duplicate:<任意、既定false>` とする。日時は `YYYY-MM-DD HH:MM`、`YYYY/M/D HH:MM`、`M/D HH:MM`、`今日 HH:MM`、`明日 HH:MM` の5形式を受理する。年省略は作成操作時点から5分以上先となる次の実在日時（2月29日を含む）として解釈し、今日指定が境界未満でも翌日へ繰り越さない。ちょうど5分後は許可する。`content` 未指定だけを下書きとし、指定された空文字、空白・改行だけ、2,000文字超過、`@everyone` または `@here` を含む本文は拒否する。重複候補がある場合は作成せず、`allow_duplicate=true` での再実行を案内する。

単発作成はローカル検証後、完全なJST日時、状態、投稿先、本文プレビュー、入力日時を示すephemeral確認Embedと、本人だけが操作できる「予約する」「キャンセル」ボタンを120秒間表示する。確認中はDB Session、トランザクション、行ロックを保持しない。確認時に完全日時を固定し、ボタン時に年や日付を再推論しない。予約ボタン時にguild、共通認可、投稿先とBot権限、本文、最新時刻での5分境界を再検証し、成功時だけ新しいトランザクションで保存する。キャンセル、timeout、再検証失敗では保存しない。autocompleteとカレンダーUIは対象外とする。

毎日予約の作成は `/post create-daily`、毎週予約は `/post create-weekly` とする。終了日は `今日`、`明日`、`明後日`、`M/D`、`YYYY/M/D`、`YYYY-MM-DD` を受理し、操作時点のJST日付から完全な日付へ正規化する。`M/D` は今日以降の次の実在日（2月29日は400年以内の次のうるう年）とし、全角数字・全角記号、タブ、存在しない日付、曖昧な自然言語は拒否する。曜日は月曜日0から日曜日6として保存する。開始日は設けず、作成時点から5分以上先にある最初の発生日時を初回投稿とし、ちょうど5分後と終了日当日を含む。初回候補が終了日を超える場合は保存しない。

## 7. 予約と定期投稿の仕様

### 7.1 共通仕様

- 対応言語は日本語だけとする。
- 利用者が入力・確認する日時は、すべて `Asia/Tokyo`（日本時間）とする。
- 編集の日時入力は従来どおり `YYYY-MM-DD HH:MM` とし、単発作成だけは上記5形式を使用できる。
- 予約は分単位とし、秒は指定しない。
- 新しい予約の日時は、作成時点から5分以上先でなければならない。
- データベースには日時をUTCで保存し、Discord上では日本時間に変換して表示する。
- 投稿先は、対象サーバー内でBotが閲覧と送信を行えるテキストチャンネルから指定する。
- 同じチャンネル、同じ日時、同じ本文の予約がある場合は、作成前に重複の可能性を警告する。
- 投稿処理中の予約は編集または削除できない。
- 次回投稿時刻の5分前を過ぎた予約は編集できない。
- `draft`または`active`は現在の次回投稿が編集確定時点から5分以上先の場合だけ編集でき、
  ちょうど5分後は許可する。本文または投稿先だけの変更にも適用する。`paused`は対象外とする。
- 編集後には、変更後の内容と次回投稿日時を表示する。
- 誰がいつ作成、編集、削除、一時停止、再開したかを記録する。
- `draft`、処理中でない`active`、`paused`、`failed`は論理削除できる。`completed`、`ended`、`deleted`、処理中または結果確定中の予約は削除できない。

### 7.2 単発予約

- 指定した日時に1回だけ投稿する。
- 投稿に成功した予約は「完了」状態にする。
- 完了した予約と関連履歴は30日間保存し、30日経過後に自動削除する。
- 完了済みの予約は編集できない。
- 単発予約は一時停止・再開できない。実行を止める場合は予約を削除する。
- 予約を削除しても、すでにDiscordへ投稿されたメッセージは削除しない。

### 7.3 毎日の定期投稿

- 毎日、指定した日本時間の同じ時刻に投稿する。
- 任意の終了日を設定できる。
- 終了日を設定しない場合は、一時停止または削除されるまで継続する。
- 作成時点から5分以上先となる最初の指定時刻を初回投稿とする。今日の指定時刻が境界未満なら翌日とする。

### 7.4 毎週の定期投稿

- 毎週、指定した1つの曜日と日本時間の同じ時刻に投稿する。
- Phase 1では、1つの予約に複数の曜日を指定できない。
- 任意の終了日を設定できる。
- 終了日を設定しない場合は、一時停止または削除されるまで継続する。
- 作成日が指定曜日で指定時刻が5分境界以上なら当日、境界未満なら7日後を初回投稿とする。別曜日なら次に到来する指定曜日とする。

### 7.5 定期投稿の編集、一時停止、再開

- 定期投稿の編集は、次回以降のすべての投稿に適用する。
- 本文または投稿先だけの編集では通常pendingと再試行待ちpendingを維持し、次回試行は
  最新の予約内容を使う。日時または繰り返し設定を変更した場合は、変更前のpendingを
  `skipped`にし、編集確定時点から5分以上先の新しいpendingを作る。ただし新候補が現在の
  pendingと同日時なら維持する。
- 定期編集では、同日時の過去runを変更・削除・再利用しない。最初の候補が使用済みなら
  終了日内の次の未使用発生日時まで進める。終了日当日を含む。
- 一時停止中は投稿先、本文、投稿時刻、曜日、終了日を編集できる。編集後も`paused`と
  `next_run_at = NULL`を維持し、自動再開しない。channelまたは本文だけの変更では保持中の未来runを維持し、
  投稿時刻、曜日、終了日の変更では旧保持runを`skipped(schedule_edited)`とする。過去の終了日も保存でき、
  次回の再開時に終了または再開拒否を判定する。
- 過去に投稿済みのDiscordメッセージや実行履歴は変更しない。
- 一時停止と再開は、毎日または毎週の定期投稿だけに使用できる。
- 一時停止中は投稿を行わない。
- pause／resume成功Embedは、状態・種別、投稿先、次回投稿・基本投稿時刻・曜日・終了日、予約IDの順に通常情報を表示し、停止・再開結果や下書き固有の案内は重複を避けて最下部の注意フィールドへまとめる。pauseでは保持runの有無にかかわらず、一時停止中はDiscordへ投稿されないことを明示する。
- 停止前の未来の通常初回runは同じID、`attempt_count=0`、DeliveryAttemptなしで保持し、予定時刻前の再開では同じrunを再利用する。この場合、成功Embedで一時停止前に保持していた投稿回を引き続き使用し、次回投稿日時が変更されていないことを明示する。
- 保持runの時刻を過ぎた後の再開は120秒の本人限定Viewで、次回から再開、同日分を今すぐ投稿、同日分の時刻指定、キャンセルを選択する。数日前の回および終了日超過後は次回から再開だけを許可する。
- 定期投稿を削除すると、今後のすべての投稿を停止する。
- 終了日の判定には `Asia/Tokyo` の日付を使用し、終了日当日の予定投稿は実行対象に含める。
- 終了日当日の最後の予定投稿を処理した後、定期投稿を `ended` 状態にする。
- `ended` 状態の予約は今後投稿せず、編集、一時停止、再開もできない。
- 一時停止は `/post pause public_id:<canonical UUIDv7>`、再開は `/post resume public_id:<canonical UUIDv7>` とし、理由、confirm、確認Viewを使用せず可逆操作として即時実行する。
- 一時停止できるのは、処理中または結果確定中ではない `active` の毎日・毎週予約だけとする。`draft`、すでに`paused`の予約、終端・失敗状態、単発予約は一時停止できない。再開できるのは、処理中または結果確定中ではない`paused`の毎日・毎週予約だけとする。
- 一時停止時点より未来で、`next_attempt_at = scheduled_for`、`attempt_count=0`、claim/leaseがNULL、DeliveryAttemptなし、Scheduleと整合する通常初回pendingを最大1件だけ保持する。到来済みpending、retry pending、DeliveryAttempt履歴を持つpendingは`skipped(schedule_paused)`とする。不整合または複数候補は操作を拒否する。
- pausedは`Schedule.next_run_at = NULL`を維持する。paused保持runはWorkerがclaimせず、Bot停止中に到来してもStartup Recoveryが健全な初回runを選択可能な状態で保持する。不整合・retryは安全側で整理する。
- 同日分の救済は利用者の明示操作で例外pending runを作り、Gatewayを直接呼ばず通常PollingWorkerへ渡す。例外run完了後は保存済みの基本投稿時刻、曜日、終了日から次回を計算する。
- 不存在、権限不足、状態不許可、処理中または結果確定中には、予約の存在を推測できない同じ応答を返し、二重操作を成功扱いにせず操作履歴も追加しない。

### 7.6 予約の状態

予約状態は、予約全体が今後どのように動くかを表す。予約は少なくとも次の状態を持つ。

- `draft`（下書き）: 本文が未入力
- `active`（有効）: 投稿可能
- `paused`（一時停止）: 利用者が定期投稿を停止中
- `failed`（失敗）: 単発投稿が最終的に失敗し、運営者の確認が必要
- `completed`（完了）: 単発投稿が成功済み
- `ended`（終了済み）: 終了日を迎えた定期投稿
- `deleted`（削除済み）: 利用者が削除済み

本文と予約状態の関係は次のとおりとする。

- `draft` は本文が未入力であり、`content` はNULLとする。
- `paused` は、削除前の編集状態に応じて本文なし・本文ありのどちらも許可する。
- `deleted` は削除前の本文をそのまま保持する。本文なしの `draft` または `paused` を削除した場合は、NULLのままとし、ダミー本文を保存しない。
- `active`、`failed`、`completed`、`ended` は本文を必須とする。

各回の投稿結果は、予約状態とは分けて実行履歴へ保存する。実行履歴は少なくとも次の状態を持つ。

- `pending`（実行待ち）: 予定されているが、まだ処理を始めていない
- `processing`（処理中）: 最初の送信または再試行を実行中
- `succeeded`（成功）: Discordへの投稿に成功した
- `failed`（失敗）: その回の投稿が最終的に失敗した
- `skipped`（見送り）: 下書き、Bot停止中の期限超過などにより投稿しなかった

定期投稿の1回が失敗しても、予約自体は原則として `active` を維持し、次回予定を実行する。単発投稿の最終失敗時だけ、予約自体を `failed` にする。

予約一覧は全件数と総ページ数を示し、既存の日時・NULL後方・内部IDによる安定順序で1ページ10件表示する。`page` と状態絞り込みを維持し、本人限定でBot稼働中はtimeoutしないViewにより前後移動、予約種類（すべて・単発・毎日・毎週）の絞り込み、現在ページの予約選択を提供する。種類変更時は状態条件を維持して1ページへ戻り、0件でも種類選択を利用できる。選択後は `/post show` と同じ詳細表示へ移り、種類・状態・ページを保ったまま一覧へ戻れる。操作ごとに最新DB状態と認可を再確認し、ページ減少時は最後の有効ページへ補正する一方、明示した範囲内の巨大pageは安全な空ページとして扱う。Bot再起動後は古いViewを復元せず、`/post list` または `/post show` の再実行を案内する。状態未指定では削除済みを除外し、`deleted` 明示時だけ含める。非管理者は自分の予約だけ、管理者は対象guild内の全予約を閲覧できる。

## 8. 下書きと通知

- 本文なしでも予約を作成でき、その予約を「下書き」とする。
- 下書きには、投稿予定日時、投稿先、繰り返し方法など、本文以外の予約情報を保存する。
- 本文が入力された時点で、有効な予約へ変更する。
- 投稿予定時刻の24時間前に、本文が未入力なら作成者へDMで通知する。
- 投稿予定時刻の1時間前にも、本文が未入力なら作成者へDMで再通知する。
- 作成時点ですでに24時間前を過ぎている場合、24時間前の通知は送らず、まだ過ぎていない次の通知だけを送る。
- 作成時点ですでに1時間前を過ぎている場合、作成直後に本文未入力であることを作成者へ通知する。
- 作成者へDMを送れない場合は、環境変数で指定した運営者通知チャンネルへ通知する。
- 下書きのまま予定時刻を迎えた場合は投稿せず、その回を `skipped` として運営者通知チャンネルへ通知する。
- 単発の下書き予約は `draft` のまま残し、自動投稿しない。作成者または管理者が本文と新しい未来の日時を設定するか、予約を削除する。
- 定期投稿では本文がない回の実行履歴を `skipped` として記録し、予約自体は下書きのまま次回予定を維持する。
- 一時停止中の定期投稿には事前通知を送らない。

通知には、予約ID、投稿予定日時、投稿先、必要な対応を含める。ただし、Botトークンなどの秘密情報は含めない。

運営者通知チャンネルへ投稿できない場合は、環境変数で指定したBot運営者へDMを試す。チャンネル通知とDMの両方に失敗した場合は、エラーをログへ残す。通知には秘密情報や内部の例外全文を含めない。

通知時刻の境界は包含とし、予定時刻のちょうど24時間前は`draft_24h`、ちょうど1時間前は`draft_1h`とする。Bot停止中に過ぎた24時間前・1時間前通知は後追い送信しない。復旧時点で予定時刻前かつ残り1時間未満のdraftだけ、発生回ごとに`draft_immediate`を1回生成する。

activeからdraftへ編集した場合、次回まで24時間以上なら通常の24時間前・1時間前、1時間以上24時間未満なら1時間前だけ、1時間未満なら即時通知を対象とする。定期draftはScheduleRun単位で通知する。pause、delete、active化、日時編集で不要になった通知は送信前の最新状態確認で`cancelled`とし、送信しない。

通知の一時失敗は初回を含め最大3回とし、1回目の失敗から1分後、2回目の失敗から5分後に再試行する。DiscordのRate Limitで未来のRetry-Afterが指定された場合はそれを優先する。恒久失敗または3回目の失敗ではフォールバックを許可する。送信結果不明では再送もフォールバックもしない。

通知は固定タイトル・説明を持つDiscord Embedとする。日本語状態名、投稿先の`<#channel_id>`形式、JST日時、完全な予約UUIDv7、必要な対応を表示し、投稿本文と本文プレビューは含めない。title、description、Field名、Field値、Field数、合計文字数のDiscord Embed上限を送信前に検証し、`AllowedMentions.none()`相当ですべてのメンション通知を無効にする。バックグラウンド通知はephemeralではない。通知のためにPrivileged Intent、Message Content Intent、Members Intent、Administrator権限を追加しない。

Recovery未完了、DB障害、通知Worker自身の障害はDiscord通知の対象にせず、安全なERRORログと外部監視の境界とする。通知Workerは起動Recoveryが完全に成功した後だけ開始する。

通知outboxは予約投稿Workerとは独立した通知Workerが処理する。1サイクルでclaimをcommitし、短い送信前再検証トランザクションを閉じてからDiscordへ1回だけ送信し、結果を別トランザクションで保存する。最大並行数、batch、poll間隔、processing leaseは通知専用設定を使用する。expired leaseのclaimedは1分・5分の規則で再試行し、sendingは結果不明として再送しない。不整合もunknownへ安全に終端化する。

permanentまたは3回上限だけ、`creator_dm → operator_channel → operator_dm → log`の順で別outbox行を冪等作成する。unknown、retry中、cancelledではfallbackを作らない。Discord経路は共通の安全なEmbedを使用する。`log`経路はDiscord Embedを送信せず、Discord APIも呼ばず、安全な固定ERRORイベントだけを記録する。

下書き事前通知はJIT生成せず、現在のScheduleRunを作成・置換する業務トランザクション内で未来outboxを事前作成する。残り24時間以上は24時間前と1時間前、残り1時間以上24時間未満は1時間前、残り1時間未満かつ未来は即時通知を作り、24時間・1時間ちょうどを各通知に含める。起動時bootstrapは固定`recovery_cutoff`より前の未claim pending事前通知だけを`cancelled`にし、後追い送信せず、現在のfuture draft Runに不足する計画を冪等作成する。旧Runやactive化・pause・delete後の通知は送信前再検証でcancelする。

bootstrapは通知batch sizeで最大25バッチとし、4種類のRecovery/Bootstrapがすべて完了した後だけ予約投稿、通知、maintenanceの3 loopを開始する。Processing Recoveryで`failed`へ終端化したrunは、同じ固定`recovery_cutoff`を`finalized_at`として、同じトランザクション内で既存のSchedule確定規則へ接続する。retry予定の`pending`へ戻したrunは確定しない。単発activeはScheduleを`failed`にしてsystem OperationLogを1件だけ残し、定期activeはScheduleを維持してcutoffより厳密に未来の次回runを1件だけ生成し、次回がなければ`ended`としてsystem OperationLogを残す。run復旧とSchedule確定は原子的であり、確定失敗時は当該バッチをrollbackして後続Recoveryと3 loopを開始しない。

draft予定時刻到来の`run_skipped`、投稿の最終failed・結果unknownの`run_failed`、起動後15分以内の`run_delayed`、Recovery不整合の`recovery`は、各状態確定と同じトランザクションで最初の`operator_channel` outboxだけを冪等生成する。業務理由は`ScheduleRun.result_code`と`notification_type`から送信直前に固定文へ再構築し、`NotificationLog.error_code`は通知配送エラー専用とする。投稿結果unknownの通知とNotificationLog配送結果unknownは別の状態であり、後者は再送・fallbackしない。定期投稿の起動中欠落回はrunごとに通知せず、Schedule UUIDv7と固定`recovery_cutoff`を用いて1 Schedule・1起動・1経路へ集約する。イベント生成者はoperator DMやlogを作らず、fallbackはNotificationWorkerだけが作る。Recovery未完了そのものはDiscord通知しない。30日後の物理削除は独立したmaintenance loopが行う。

## 9. 失敗時の再試行

最初の送信を1回行い、一時的な通信障害などで失敗した場合は、次の間隔で最大3回再試行する。

1. 1分後
2. 5分後
3. 15分後

したがって、最大試行回数は最初の送信1回と再試行3回を合わせた合計4回である。

Discordから再試行までの待機時間を指定された場合は、その指示を優先する。

次のように再試行しても解決しないと判断できる場合は、再試行せず直ちに失敗とする。

- Botに投稿権限がない
- 投稿先チャンネルが削除されている、または存在しない
- Botが対象サーバーから退出している
- 投稿内容がDiscordの制限に違反している

最大回数の再試行に失敗した場合は、その実行を失敗として記録し、運営者通知チャンネルへ通知する。

単発予約は `failed` 状態にする。定期投稿では失敗した回の実行履歴を `failed` とし、予約自体は原則として `active` を維持して次回予定を実行する。

各実行には一意な識別情報を持たせ、同じ実行を重複して送信しないようにする。送信結果が不明な場合も、無条件に再送して二重投稿を発生させない設計とする。

## 10. Bot停止・復旧時の動作

- 予約と実行状態はPostgreSQLへ保存し、Botを再起動しても失われないようにする。
- Bot起動時に、未完了の予約と投稿処理をデータベースから読み込み直す。
- 同じBotが複数起動した場合でも、同じ予約を二重実行しないようデータベースを使って排他制御する。

### 10.1 期限を過ぎた単発予約

Bot復旧時に単発予約の予定時刻を過ぎていた場合は、次のように処理する。

- 予定時刻から15分以内なら、遅延投稿を行う。
- 15分を超えていたら自動投稿せず、予約を `failed` 状態にする。
- 遅延投稿を行う場合も、自動投稿しない場合も、運営者通知チャンネルへ通知する。

15分以内の遅延投稿がDiscordへの送信エラーになった場合は、通常の再試行ルールを適用する。

### 10.2 期限を過ぎた定期投稿

- Bot停止中に過ぎた回は投稿しない。
- 抜けた回数と停止していた期間を実行履歴へ記録する。
- 復旧時点より後にある最初の予定日時を計算し、次回投稿とする。
- 投稿できなかった回があることを運営者通知チャンネルへ通知する。

### 10.3 投稿処理中に停止した場合

- 起動時に未完了の投稿処理を検出する。
- Discordへの送信が成功したか確認できない場合は、二重投稿防止を優先する。
- 自動で安全に再開できない実行は、実行履歴を `failed` として運営者へ確認を依頼する。単発予約は `failed`、定期投稿の予約は原則として現在の予約状態を維持する。

### 10.4 起動時復旧の確定境界

- 起動Recovery全体でUTCの同一時刻を基準時刻として固定し、処理中実行の復旧とpending実行の復旧に共通利用する。
- 単発activeの初回pendingは予定時刻から15分以内（ちょうど15分を含む）だけ遅延投稿対象として維持し、15分を超えた場合は投稿せずrunを`skipped`、予約を`failed`にする。
- 単発draftは予定時刻に達したらrunを`skipped`にし、予約の`draft`、`next_run_at`、versionを維持する。
- 通常の再試行待ちpendingは15分ルールの対象外とし、`next_attempt_at`に従う。
- 毎日・毎週の過去回は15分以内でも投稿せず、欠落回を含めて`skipped`として保存し、基準時刻より厳密に未来の未使用回を1件だけ作る。
- startup Recoveryでは`paused`を自動的に`ended`へ変更しない。
- Recovery中はDiscord APIを呼ばない。処理中実行とpending実行の両Recoveryが完全に成功した後だけ通常ポーリングを開始する。
- 運営者通知用NotificationLogは、Recoveryで状態を確定する同じトランザクション内で冪等生成する。

## 11. データ保存

### 11.1 データベース

- データベースにはPostgreSQLを使用する。
- 開発環境のPostgreSQLはDocker Composeで起動する。
- PythonアプリケーションはDockerコンテナ内ではなく、WSL上の `.venv` で実行する。
- PostgreSQLの接続先や認証情報は環境変数で設定する。
- 開発、テスト、本番のデータベースと認証情報を分離する。

### 11.2 保存する主なデータ

- 予約ID
- 対象DiscordサーバーID
- 作成者のDiscordユーザーID
- 投稿先チャンネルID
- 投稿本文
- 単発、毎日、毎週の種別
- 毎週投稿の曜日
- 次回投稿日時
- 任意の終了日
- 予約状態
- 再試行回数と次回再試行日時
- 作成日時と更新日時
- 作成、編集、削除、一時停止、再開を行った利用者と日時、およびシステムによる単発完了、失敗、定期終了の履歴
- 各回の予定日時、実行日時、結果、エラーの概要
- Discordへ投稿できた場合のメッセージID
- 下書き通知の送信日時と結果

Discordの表示名やチャンネル名は変更される可能性があるため、識別にはDiscordが発行するIDを使用する。

`completed`、`ended`、`deleted` 状態の予約と、それらに関連する履歴は`terminal_at`から30日間保存し、30日ちょうどを含めて自動削除する。`failed`状態のままの予約は自動削除しない。failedから作成者の`creator_deleted`、管理者の`admin_deleted`または`operator_resolved_failed`で`deleted`になった予約は、削除前状態やdelete kindで区別せず、deletedへ遷移した`terminal_at`から30日後に削除する。`creator_deleted`は運営者確認を意味しないが、権限を持つ作成者による明示的削除として保持期間を開始する。物理削除後の予約単位の監査履歴は保持せず、すでに投稿済みのDiscordメッセージは削除しない。運用に必要なバックアップと復元手順を用意する。

ScheduleまたはRunに関連する通知を含む関連行にpending、processing、claimed、sendingのin-flight状態が1件でもあれば物理削除しない。ScheduleとRunの両方に関連しないglobal NotificationLogは終端状態の`finished_at`から30日保持する。cleanupは1サイクルで固定したUTC時刻を基準に、Schedule最大100件とglobal通知最大100件を別枠で処理し、個別transactionの失敗や未完了によって予約投稿・通知処理を停止しない。

## 12. セキュリティ

- DB schema変更の正式経路はPython Migrationラッパーとし、Alembic CLI直接実行とoffline modeを禁止する。
- DB接続を伴うMigration操作は、実行ごとにtargetと期待DB名を明示し、URL上のDB名に加えて接続後の`current_database()`が完全一致するまでDDLを開始しない。
- testは`discord_bot_test`、developmentは`discord_bot_dev`だけを許可する。productionは実DB名を明示できない場合にfail-closedとし、名前を推測しない。
- `upgrade`、`downgrade`、`stamp`、`autogenerate`は`target:database:operation`に完全一致する確認値を要求する。`current`と`check`は確認値を要求しないがDB identity照合を省略しない。
- testは実行プロセスの`TEST_DATABASE_URL`だけ、productionは実行プロセスの`DATABASE_URL`だけを使用し、別環境や`.env`へfallbackしない。developmentだけは既存の`DATABASE_URL`／`.env`を使用できる。
- Migrationの通常ログとエラーへURL、user、host、port、passwordを出さない。Bot起動時の読み取り専用schema verificationと既存Revision固有downgrade guardは維持する。

- Discord Botトークン、データベースのパスワードなどの秘密情報をGitへコミットしない。
- ローカル環境では `.env` を使用し、Gitには秘密情報を含まない `.env.example` だけを置く。
- 対象DiscordサーバーID、許可ロールID、Bot運営者ユーザーID、運営者通知チャンネルIDを環境変数で指定する。
- Botには動作に必要な最小限のDiscord権限だけを与える。
- コマンド実行時に、対象サーバー、利用者のロール、管理者権限、予約の所有者を確認する。
- Phase 1では、すべての利用者について `@everyone` と `@here` の使用を禁止する。
- 予約の登録・編集時に `@everyone` と `@here` を拒否する。
- Discordへ送信するときは `allowed_mentions` を明示的に指定し、`@everyone` と `@here` が通知として働かないよう制限する。
- ユーザーやロールへの通常メンションも、意図しない通知を防ぐため、Phase 1では原則として解析・通知しない設定にする。
- ログや運営者通知にBotトークン、データベース認証情報、接続文字列を出力しない。
- 運営者通知チャンネルへ投稿できない場合はBot運営者へのDMを試し、両方に失敗した場合はログへ記録する。
- 運営者への通知には秘密情報や内部の例外全文を含めない。
- 利用者向けのエラー表示には内部の例外全文を載せず、必要な対応を日本語で示す。
- データベースのバックアップはアクセスを制限し、復元できることを確認する。

## 12.1 Phase 2: 予約ID Autocomplete

- `/post show`、`edit`、`delete`、`pause`、`resume`の必須`public_id`へ候補を表示する。
- 候補値は完全なcanonical UUIDv7とし、候補を使わないUUIDv7直接入力も維持する。
- 管理者には設定guild内の全作成者、許可ロール利用者には本人所有の候補だけを表示する。
- DM、設定外guild、不完全なInteraction、認可失敗、DB・表示処理失敗では空候補とする。
- 候補は最大25件、`next_run_at ASC NULLS LAST, id ASC`の安定順とする。
- 候補名は状態、種別、JST日時、キャッシュ済みchannel名、UUID末尾6文字だけで構成し、本文や内部IDを含めない。
- 検索は投稿先チャンネル名を基本とし、前後空白と先頭の`#`1個を検索時だけ除き、casefoldした完全一致・前方一致・部分一致を許可する。日本語を含むUnicodeへ無条件NFKCを適用せず、曖昧検索・編集距離・類義語・本文検索は行わない。UUID前方・完全一致、固定された日英の種別・状態名、数値channel ID完全一致も維持し、同じ入力に複数条件が一致すればORで重複なく統合する。
- チャンネル名はDBへ保存・送信せず、設定guildのキャッシュ済みTextChannelだけからBot層で安全なchannel ID集合へ解決する。別guild、Thread、DM、Category、Voice、実行者が閲覧不能なchannelを除き、REST取得は行わない。空文字・`#`だけは名前検索せず、制御文字・改行・ゼロ幅文字・100文字超は空候補とする。
- showは閲覧可能な全状態（deletedを含む）、他の操作は既存の状態・run・attempt規則で明確に操作不能な予約を除外する。
- 候補は参考情報であり、実行時の認可、状態、version、run、attempt、row lockによる再検証を省略しない。
- Autocompleteは読み取り専用とし、Discord REST追加取得、DB更新、モデル・Migration・Intent・Bot権限追加を行わない。

## 12.2 Phase 2: 予約詳細View基盤

- `/post show`と`/post list`の選択後は、同じ予約詳細DTOと詳細Contextを使用する。DTOは正の`version`を内部用に持つが、Embedへ表示しない。
- 詳細取得時に状態、種別、current run、pending run、processing run、DeliveryAttempt、5分境界をread-onlyで観測し、編集・一時停止・再開・削除の表示用可否を不変DTOで返す。可否は参考情報であり、将来の操作時も既存Application Serviceの再検証を最終判断とする。
- 第1段階では未接続の操作ボタンを表示しない。直接showは空Viewを送らず、一覧由来だけ固定custom IDの「一覧へ戻る」を表示する。
- 一覧由来の詳細Contextは状態、種類、ページを保持する。戻る操作では最新の認可、予約所有境界、一覧を再取得し、末尾ページ消滅時は最後の有効ページへ補正する。
- 詳細Viewは本人限定、ephemeralで、Bot稼働中はtimeoutしない。Bot再起動後は復元せず、古い画面の操作時は `/post show` または `/post list` の再実行を案内する。
- View待機中にSession、transaction、row lockを保持せず、Bot終了時は一覧・詳細・既存確認ViewとModalを停止してwaitを回収する。

## 12.3 Phase 2: 予約詳細からの状態操作

- 詳細Viewは状態と操作可否に応じて一時停止、再開、削除を提供する。編集UIは提供しない。
- 詳細表示時versionをexpected versionとして更新Serviceへ渡し、不一致を固定の競合案内で拒否する。
- 操作後はcommit後の新しいread Sessionで詳細を再取得し、同じephemeralメッセージを更新する。
- 管理者が他人の予約を削除する場合だけ、1～500文字の理由入力を必須とする。
- 編集可能な詳細には編集ボタンを表示し、単発・毎日・毎週ごとのModalで最大5項目を一度に原子的に編集できる。本文と終了日は空欄で解除する。
- 詳細編集Modalは900秒、操作者本人限定とし、待機中にDB資源を保持しない。競合時は古い初期値を適用せず最新詳細へ戻す。

## 12.4 Phase 3とPhase 2後の将来計画

以下はPhase 2の完了条件に含めないPhase 3の要件である。`/post show`の削除済み候補除外、予約名基盤2A、Provider非依存基盤2B、OpenAI Adapter隔離実装2C-1、実Provider受入の安全基盤2C-2までを実装済みとする。実Provider通信、品質・保持・請求受入、モデル正式採用は未実施である。

### `/post show`の削除済み候補

- Phase 3第1段階として、通常のAutocomplete候補母集合から`deleted`予約を除外する。空入力、状態、種別、UUID、channel ID、channel名の各検索と、所有者・管理者のどちらにも適用する。
- `deleted`予約自体と監査履歴はDBへ保持し、30日保持規則を変更しない。
- `deleted`予約は`/post list status:削除済み`から確認でき、一覧から削除済み詳細を開けるようにする。
- canonical UUIDを直接入力した場合は、`/post show`で削除済み詳細を表示できる互換性を維持する。
- delete、edit、pause、resumeの既存状態境界は変更せず、候補表示だけを整理する。

### AI予約名

- AIの用途は現在の投稿本文から最大32文字の予約名を1件生成することだけに限定し、利用者の事前確認を必須とせず自動採用する。生成名では改行と制御文字を禁止する。
- `/post list`、`/post show`、Autocomplete候補、確認画面へ予約名を表示し、利用者は詳細画面の✏️編集から後で変更できるようにする。候補へ予約本文または本文の一部を表示しない。
- 名前の由来はAI生成を`source=ai`、利用者編集を`source=manual`、未設定を`source=unset`として区別する。`manual`は本文変更後も維持し、AIが自動で上書きしない。
- `ai`の状態で本文が変更された場合は古いAI名を解除して再生成を1回だけ試す。失敗時は`unset`とし、古いAI名を残さない。
- AI生成名は親Scheduleの一部として保存し、親Scheduleと同時に削除する。AI入力とAI応答の履歴は保存しない。
- 利用者ごとの文体・文脈・過去投稿を学習する機能、利用者プロファイル、過去投稿検索、Embedding、ベクトルDB、ファインチューニング、恒久的な学習データセットを作成しない。
- 2Aでは`schedules.display_name VARCHAR(32)`と`schedules.display_name_source VARCHAR(8)`を追加する。既存行と名前解除は`NULL/unset`、有効な手動編集は`manual`とし、将来のAI生成名だけを`ai`とする。
- 共通詳細Viewの独立Modalから、draft、active、pausedの予約名を所有者または同guild管理者が編集できる。空欄は解除、同値はno-opとし、実変更だけversionと本文を含まないOperationLogを更新する。
- View、Button、SelectとModal内入力部品は用途別の固定custom IDを維持する。discord.pyのModal dispatchは外側custom IDだけをキーにするため、外側Modalだけは用途別固定prefixと32桁の非識別ランダムnonceを組み合わせ、100文字以内とする。nonceへ予約・利用者・guild・channel・version・本文・名前・理由・秘密情報を含めない。同種Modalを複数同時保持し、新規Modalを開く操作で別端末、別詳細、別予約、別利用者のModalを停止しない。
- Modalはsubmit、timeout、error時に自分自身だけをregistryから解除し、同一Modalの二重submitをロックと終了状態で防ぐ。閉じる操作はDiscordから通知されないため有限timeoutで回収し、Bot closeではregistry内の全Modalをsnapshotしてstop・wait回収する。
- 名前Modalはsubmit時のInteractionからguild、許可ロール、所有者・管理者境界を再検証する。詳細表示後に権限を失い、最新詳細を安全に再取得できない場合は旧Viewを解除し、他人予約のEmbedや本文、名前、投稿先、UUIDを再表示せず、`現在の権限ではこの予約を編集できません。/post showを再実行してください。`だけを`AllowedMentions.none()`付きで返す。defer済みの場合も元のephemeral応答をこの固定案内へ更新し、想定される認可拒否をERRORにしない。
- 本文変更時はmanual名を維持し、ai名だけ即座に解除する。2Aでは再生成処理を開始しない。

### 非AIフォールバック

- 非AIフォールバック名はDBへ保存しない。
- 単発は`単発予約 M/D HH:MM`、毎日は`毎日予約 HH:MM`、毎週は`毎週予約 曜日 HH:MM`とし、必要な日時がない場合は`名称未設定`とする。
- 本文または本文の一部をフォールバック名、一覧、詳細の名称欄、Autocomplete候補へ表示しない。

### AI費用・可用性・プライバシー

- AIは初期状態で無効とし、明示設定時だけ有効化する。
- 同じSchedule versionにつき最大1回、timeoutは5秒、自動再試行は行わない。
- 50回／日、500回／月、100円相当／月は、Provider未選定・未接続の開発段階と2B初期実装・隔離テストで使う変更可能な安全設定値とする。販売価格や正式リリース時の恒久上限ではなく、コード定数やDB制約へ変更不能な値として固定しない。2CのProvider選定時と商品仕様策定時に再計算する。
- 運営者全体のBudgetは設定から`BudgetPolicy`へ渡す。不正値、未設定、価格不明、集計失敗、上限到達時は安全側でAIを呼ばない。顧客プランQuotaは将来の別Policy・別集計とし、2Bでは決済や顧客Quotaを実装しない。
- 2B-1では`name_generation_jobs`と全体Budget bucketを永続化し、AI有効・Generator利用可能・本文あり・名前unsetの場合だけ作成または本文実変更と同じtransactionでJobを冪等登録する。AI無効、manual名、本文消去、本文以外の編集、no-opでは登録せず、既存予約を自動backfillしない。
- 2B-1のRecoveryはlease切れprocessingを再呼び出さず`abandoned/startup_abandoned`へ移し、予約済みBudgetを返却しない。Jobは完了後30日、Budget bucketは期間終了後90日保持する。Worker、Generator実行、Bot lifecycle接続は2B-2で実装する。
- 2B-2はpendingを安定順で1件claimし、Schedule、Job、JST daily、JST monthlyの順にlockして回数と最大想定費用を悲観予約する。commitとSession close後だけGeneratorを最大1回呼び、自動再試行せず、5秒timeoutと固定result codeで別transactionへfinalizeする。
- startupでは既存Recoveryとともにlease切れJobを先に回収し、利用可能なGeneratorがある場合だけpollを開始する。shutdownでは新規pollを止め、実行中taskをcancel・awaitし、可能なら`abandoned/shutdown_unknown`を保存する。cleanup loopはJob30日、bucket90日を適用し、pending／processingとSchedule blockerを維持する。
- 本番DIは`DisabledNameGenerator`だけで、AI初期無効、Provider SDK・HTTP client・APIキーなしを維持する。2B-2では外部AI、Entitlement、Plan、顧客Quota、決済を実装しない。
- 2C-1はOpenAI公式Python SDKをAdapter内部だけで使用し、Domain、Application、WorkerからSDKを参照しない。Provider／AI初期無効、APIキー未設定を維持し、全設定が有効な場合だけAdapterを構成できる。通常pytest、CI、通常起動から実APIを呼ばない。
- OpenAIの通常候補は`gpt-5.6-luna`、品質優先比較候補は`gpt-5.4-nano-2026-03-17`とする。前者に日付付きsnapshotが公式公開されていないためaliasを定期監査し、後者は比較時に固定snapshotを優先する。Deprecatedの`gpt-5-nano`、日付固定されない`gpt-5.4-nano`、未知モデルを拒否する。実API限定比較前はどちらも正式採用済みとしない。
- AdapterはstatelessなResponses API、構造化出力、`store=false`を使い、tools、web／file search、background、conversationを使わない。本文、固定instruction、`ja-JP`、32文字・単一行・禁止文字なしという条件だけを送信し、ID、UUID、version、日時、投稿先、契約情報を送信しない。
- 既存本文上限2,000文字に加えてUTF-8 byte数と保守的token上限を適用し、超過または不正応答をProvider非依存の固定分類へ変換する。JSON型、候補数、空、複数行、32文字超過、Cc／Cf／Csを検証後、既存Domain validatorを最終防御とする。
- SDK自動再試行は0、接続timeoutとrequest timeoutは既存5秒未満とする。429、5xx、接続失敗、timeout、cancel、認証・モデルエラーで再呼び出しせず、既存Budgetを返却しない。APIキー、本文、生成名、応答、Provider request ID、実usage、例外全文をJob、Budget、OperationLog、通常ログへ保存しない。
- 将来は`AI設定 → Entitlement → 顧客プランQuota → ModelSelectionPolicy → 運営Budget → Job → Generator`とする。2C-1では運営設定の単一モデルだけを扱い、Plan、Entitlement、顧客Quota、ModelSelectionPolicy、契約、決済を実装しない。運営Budgetと顧客Quotaは別責務・別集計を維持する。
- Provider側の標準的なabuse monitoring保持最大30日を2C-1時点では許容する。学習利用のopt-inは行わず、ZDRと国内処理要件は正式公開前に再評価する。ProviderがAPIデータを既定で学習に使わないことと、Bot自身が文体学習、過去投稿学習、Embedding、プロフィール生成を持たないことを別の方針として維持する。
- 2C-2は実Provider受入そのものではなく、明示許可後だけ使用できる独立手動CLIの安全基盤とする。通常Bot、Worker、通常pytest、DB、永続Job／Budgetからlive runnerへ接続せず、固定6件の匿名合成本文を選択した許可モデルへ各1回だけ直列送信する。任意本文、stdin、ファイル、DBからの入力、再開、自動retry、model fallback、並列呼出しを追加しない。
- live実行はProvider、専用target、明示モデル、最大request数、悲観最大JPY microunits、操作を束縛した完全一致confirmationと、process環境だけの専用APIキーが揃う場合に限る。公式`https://api.openai.com/v1`を固定し、redirect、proxy環境、任意base URLを許可しない。DNSや経路上の攻撃をアプリケーションだけで完全には防げないため、専用Projectと実行環境のネットワーク管理も実Provider受入条件とする。
- 手動受入の上限は既存の監査済みモデル単価、JPY microunits為替、安全係数、入出力token上限からprocess内で悲観計算する。DBの運営Budgetや将来の顧客Quotaとは接続せず、request開始前に回数と費用を消費済みにし、timeout、cancel、結果不明でも返却しない。表示額は受入試験の安全見積りで販売価格ではない。
- live時だけcase ID、モデル、検証済み生成名、文字数、経過時間、消費request数、悲観費用累計を対話標準出力へ表示できる。合成本文全文、APIキー、header、raw request／response、Provider request ID、raw usage、例外全文を表示せず、ファイル、DB、Job、Budget、OperationLog、通常loggerへ自動保存しない。shell redirectによる実行者側の保存は防止不能であることを運用手順へ明記する。
- 実Provider受入は公開前へ延期し、中止または不要とは扱わない。専用Projectは準備済みだが、Project名・ID等を保存せず、残高0 USD、支払い方法未登録、APIキー未作成、API通信0回、費用発生なしを維持する。課金可能な状態を作る前に利用者の明示許可を再取得する。
- 実Provider受入では固定匿名6 caseを`gpt-5.6-luna`へ6回、別runで`gpt-5.4-nano-2026-03-17`へ6回実行し、両runとも各requestの間隔を60秒以上空ける。Projectの各候補モデルに設定された60,000 TPM、10 RPMを超えず、retry、fallback、Batch、並列実行、自動保存を行わない。最低プリペイド購入が必要な場合もAuto-rechargeを無効にし、購入額をAPI試験原価と扱わない。
- 現在の監査条件による悲観費用はLuna 333,600 JPY microunits／回、GPT-5.4 nano 334,200 JPY microunits／回、12回合計4,006,800 JPY microunits（約4.0068円）である。実施時に日本語品質、32文字、応答時間、token、請求、保持、dashboard設定を確認し、モデルの正式な使い分けはその後、プラン別モデル・回数・機能は商品仕様策定時に確定する。
- 利用者が実用上問題なく使える品質、回数、応答速度を確保し、そのうえで重複呼び出し、無制限再試行、不要な長文入力・過剰出力、不要な高価格モデル、無期限保存を避ける。コスト削減によって通常利用を困難にしたり、頻繁にフォールバックへ落としたりしない。
- AI無効、上限到達、timeout、異常応答でも予約の作成、編集、投稿を成功させる。
- 一覧、詳細、Autocomplete、投稿Worker、Recovery、通知WorkerからAIを呼ばない。
- AIへ送るデータは現在の本文と固定生成条件だけに限定し、guild ID、利用者ID、channel ID、予約ID、内部DB ID、過去投稿、履歴など不要な識別情報を送信しない。
- AI入力本文をアプリケーション側の別履歴として保存しない。APIキー、本文、AI入力全文、AI応答全文を通常ログへ記録しない。文体学習、過去投稿学習、Embedding、利用者プロフィール、無期限保存を採用しない目的は、個人情報と投稿データの最小化、不要なプロファイリングの防止、漏えい時の影響軽減、利用者へ説明しやすく削除依頼へ対応しやすい設計、過度な複雑化の回避であり、費用削減だけを理由としない。
- AI呼び出し中にDB Session、transaction、row lockを保持しない。外部AIの用途、送信先、保存方針を利用者へ明示し、本文中の命令をAIのシステム指示として扱わない。

### Phase 3のデータ保持候補

- `active`は機能上必要な間だけ保持する。
- `completed`、`ended`、`deleted`は現行どおり`terminal_at`から30日保持する。
- `failed`は最終更新から90日を整理候補とし、実装前に削除、匿名化、通知要否を確定する。
- `draft`、`paused`は最終更新から180日を整理候補とする。30日前通知と通知失敗時の扱いを実装前に確定し、それまでは自動削除を有効化しない。
- アプリケーションログは14日、DBバックアップは日次7世代かつ最大14日保持する。
- 保存期間を過ぎたデータの削除または匿名化を自動化し、復元後のDBにも保存期限切れデータへのcleanupを適用する。
- バックアップから即時消去できない期間を利用者向け方針へ明記する。Discordへ投稿済みのメッセージはDB cleanupの対象外とする。

- 現在はローカル環境で開発し、一般公開準備まで常時稼働環境を構築しない。
- 開発、公開前限定テスト、本番でDiscord Application、DB、秘密情報を分離する。
- 一般公開直前に少人数・短期間の限定テストを行い、実Discord、権限差、複数利用者競合、長時間稼働、再起動・Recovery、バックアップを確認する。
- 限定テスト合格後は無料の常時稼働環境を第一候補とし、不足する場合だけ有料環境を検討する。Dockerで移行可能な構成を維持し、クラウド固有機能を必須にしない。
- Phase 3受入表はPhase 3実装開始時に、Phase 1・Phase 2とは別文書として新規作成する。

### ポートフォリオ掲載要件

Phase 3第6項は6A要件定義、6B成果物作成、6C最終監査に分割する。6Aの正本は[ポートフォリオ掲載計画](portfolio-plan.md)とし、実装済み、自動隔離テスト済み、実Discord確認済み、設計のみ、延期中、未実装、将来計画を区別する。一般公開、本番運用、実Provider、ARM64、契約・決済等の未確認実績を完成扱いにしない。

6Bは本文・Mermaid成果物の6B-1と画像成果物の6B-2に分ける。6B-1はREADMEを短い入口とし、[architecture](portfolio/architecture.md)、[feature flows](portfolio/feature-flows.md)、[security and privacy](portfolio/security-and-privacy.md)、[verification](portfolio/verification.md)、[screenshot policy](portfolio/screenshot-policy.md)、[asset manifest](portfolio/assets/manifest.md)へ詳細を分離する。短いEnglish summaryは利用者承認済みの最終文面を使用する。6B-2は合成データ画像4枚を匿名化・metadata監査し、READMEとfeature flowsへ組み込み済みである。Git履歴、商標、公開状態を含む最終監査は6Cへ残す。

ポートフォリオは日本語を主言語とし、README冒頭に短いEnglish summaryだけを置く。READMEは概要と入口に限定し、構成、フロー、安全性、検証、画像方針は`docs/portfolio/`へ分離する。実利用者データ、実ID、秘密、接続情報を使用せず、画像は専用開発guildの合成データで新規撮影する。元画像、復元可能なマスク、metadata付きassetをGitへ含めず、公開assetごとにmanifestを作る。

再現手順は開発DBとtest DB、通常BotとAI Provider受入を分離する。OpenAIは初期disabledとし、通常READMEにはProvider受入CLIのdry-runまでしか掲載しない。ライセンス、依存ライセンス、Discord／OpenAIの商標・画面条件、Git履歴の秘密情報は公開前の6Cで確認し、未確認の法的適合を断定しない。

## 13. β版の完成条件

次の条件をすべて満たしたとき、Phase 1のβ版を完成とする。

### 13.1 基本機能

- [ ] 環境変数で指定した1つのDiscordサーバーだけで利用できる。
- [ ] 操作とメッセージが日本語で提供される。
- [ ] 日時がすべて日本時間で入力・表示される。
- [ ] 権限のある利用者がスラッシュコマンドで単発、毎日、毎週の予約を作成できる。
- [ ] 単発予約が予定日時に1回だけ投稿される。
- [ ] 毎日および毎週の定期投稿が予定どおり実行される。
- [ ] 予約の一覧と詳細を確認できる。
- [ ] 権限のある利用者が予約を編集・削除できる。
- [ ] 定期投稿を一時停止・再開でき、停止中の回がまとめて投稿されない。
- [ ] 単発予約は一時停止・再開できず、削除によって停止できる。
- [ ] 終了日当日の投稿後に定期投稿が `ended` になり、それ以後実行・編集・一時停止・再開されない。

### 13.2 権限

- [ ] サーバー管理者と許可ロールを持つメンバーだけが予約を作成できる。
- [ ] 一般メンバーは予約を作成できない。
- [ ] 作成者は自分の予約を操作できる。
- [ ] サーバー管理者はサーバー内のすべての予約を操作できる。
- [ ] 管理者ではない利用者は他人の予約を操作できない。

### 13.3 下書きと通知

- [ ] 本文なしの予約を下書きとして保存できる。
- [ ] 下書きの24時間前と1時間前に作成者へDM通知できる。
- [ ] DMできない場合に運営者通知チャンネルへ通知できる。
- [ ] 下書きのまま予定時刻になった投稿は送信されない。
- [ ] 下書きで投稿されなかった回が、決められた状態と履歴で記録される。

### 13.4 障害と復旧

- [ ] 最初の送信に失敗した場合、1分後、5分後、15分後に最大3回再試行し、初回を含めて最大4回試行する。
- [ ] 権限不足など回復不能なエラーは再試行せず失敗にできる。
- [ ] 最終的な失敗が運営者通知チャンネルへ通知される。
- [ ] 運営者通知チャンネルへ投稿できない場合はBot運営者へDMし、両方に失敗した場合はログへ記録される。
- [ ] 同じ予約が二重投稿されない。
- [ ] Botを再起動しても予約が失われない。
- [ ] 期限から15分以内の単発予約が復旧後に遅延投稿され、運営者へ通知される。
- [ ] 期限から15分を超えた単発予約が投稿されず `failed` 状態になり、運営者へ通知される。
- [ ] Bot停止中に過ぎた定期投稿が投稿されず、次の予定から再開される。

### 13.5 データとセキュリティ

- [ ] 開発環境のPostgreSQLをDocker Composeで起動できる。
- [ ] PythonアプリケーションをWSL上の `.venv` から実行できる。
- [ ] 予約、実行履歴、通知結果がPostgreSQLへ保存される。
- [ ] 予約状態と各回の実行結果が分けて保存される。
- [ ] `completed`、`ended`、`deleted` と関連履歴が30日後に自動削除され、未確認の `failed` は自動削除されない。
- [ ] 開発、テスト、本番のデータベース設定が分離される。
- [ ] 秘密情報がGitやログへ保存されない。
- [ ] `@everyone` と `@here` を含む本文の登録・編集が拒否される。
- [ ] Discord送信時の `allowed_mentions` が明示的に制限される。

### 13.6 品質と運用

- [ ] 予約日時の計算、権限判定、状態変更、再試行、停止後の復旧に自動テストがある。
- [ ] DiscordやPostgreSQLの障害を想定した自動テストがある。
- [ ] 単発、毎日、毎週について、予約作成から投稿までを対象サーバーで手動確認できる。
- [ ] Bot停止、再起動、遅延、投稿失敗の手動確認が完了している。
- [ ] セットアップ、起動、停止、バックアップ、復元、障害確認の手順が文書化されている。
- [ ] 別の開発環境でも、手順に従ってPostgreSQLとBotを起動できる。
## GitHub公開前のリポジトリ運営要件

- オープンソースライセンスは付与せず、独自コード・文書を`Copyright (c) 2026 Oto. All rights reserved.`として公開準備する。GitHub利用規約上の閲覧・forkを除き、複製、改変、再配布、転載、二次利用、商用利用には著作権者の明示的な書面許可を必要とする。依存物・第三者素材・商標には各権利者の条件を適用する。

- CI構成、ローカル検証、GitHub上の実行成功を対象commitと日付で区別して記録し、成功確認済みの実workflowだけをbadgeから参照する。CI成功をpublic化や6C全体の完了証跡にしない。
